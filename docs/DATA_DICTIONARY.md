# Data Dictionary

All tables are synthetic, generated by `pipelines/run_data_generation.py`
from `harbor.data.generate_synthetic_data`. Schemas are enforced at runtime
by `harbor.data.validate` against the definitions in `harbor.data.schema`.

## `accounts.csv`

One row per account. Primary key: `account_id`.

| column | type | description |
|---|---|---|
| `account_id` | int | primary key |
| `plan_tier` | str | `starter` / `growth` / `enterprise` |
| `industry` | str | one of 6 categories |
| `employee_size_band` | str | `micro` / `small` / `mid_market` / `enterprise` |
| `region` | str | `na` / `emea` / `apac` / `latam` |
| `signup_month_offset` | int | months of tenure the account already had at `month_index=0` |
| `base_mrr` | float | contracted monthly recurring revenue |

## `monthly_usage.csv`

One row per (`account_id`, `month_index`). Primary key: the pair.

| column | type | description |
|---|---|---|
| `month_index` | int | 0..29 (30 months of simulated history) |
| `active_users` | float | seats actively using the product that month |
| `login_count` | float | login events that month |
| `api_calls` | float | API calls that month |
| `feature_adoption_count` | float | distinct features used that month |
| `mrr` | float | 0 once the account has churned |
| `is_active` | bool | false from the churn month onward, permanently |
| `churned_this_month` | bool | **the raw churn event** -- true only in the exact month the account churned |

**Target variable** (`churn_within_horizon`, built in `build_features.py`,
not present in this raw table) is derived as
`max(churned_this_month)` over `[snapshot_month, snapshot_month + horizon)`,
strictly after the feature window. This separation is enforced by a runtime
assertion (`_assert_no_leakage`), not just a naming convention.

## `support_tickets.csv`

One row per ticket. Primary key: `ticket_id`.

| column | type | description |
|---|---|---|
| `account_id` | int | foreign key -> `accounts.account_id` |
| `month_index` | int | month the ticket was filed |
| `category` | str | `billing` / `bug_report` / `feature_request` / `onboarding` / `cancellation_intent` / `general_praise` |
| `text` | str | synthetic ticket body |

**Known data-quality features, deliberately injected, not bugs:**
- ~6% of tickets have their recorded `category` randomly reassigned to a
  different category than the template used to generate the text --
  simulating a human agent mis-tagging a ticket. This is why the NLP
  classifier in `docs/EVALUATION_REPORT.md` scores ~0.97 F1, not 1.00.
- ~45% of tickets have a shared, category-agnostic filler sentence mixed
  into the text (greetings, sign-offs) to prevent the classification task
  from being trivially separable on category-specific keywords alone.

## `experiment_assignments.csv`

One row per RCT-eligible account (a subset of `accounts`, restricted to
those with the steepest recent engagement decline at the experiment's
`assigned_month`). Primary key: `account_id`.

| column | type | description |
|---|---|---|
| `assigned_month` | int | the month the experiment was run (`config.data.observation_cutoff_month`) |
| `group` | str | `treatment` (received a retention outreach/offer) or `control` |
| `engagement_segment` | str | `low_engagement` / `high_engagement`, split by decline severity **within** the eligible population |
| `baseline_risk_proxy` | float | the observable decline-ratio feature used for eligibility and segmentation |
| `true_p0` | float | **debug/validation only** -- the simulated counterfactual control-arm churn probability |
| `true_effect` | float | **debug/validation only** -- the simulated true causal effect of treatment (negative = churn reduced) |
| `observed_churn_90d` | bool | the actual (noisy) outcome the models are trained/evaluated on |

`true_p0` and `true_effect` exist **only because this is synthetic data**;
they are never used as model features (that would be leaking the ground
truth into the thing being validated) -- they are used exclusively in
`evaluate_uplift_method` to check whether the S-/T-learner recovers the
known effect. A real experiment would never have these columns.

## `feature_store.parquet` (generated, not raw)

One row per (`account_id`, `snapshot_month`). See `NUMERIC_FEATURE_COLUMNS`
/ `CATEGORICAL_FEATURE_COLUMNS` in `harbor/features/build_features.py` for
the full engineered feature list (trailing 3/6/12-month usage averages,
login-trend ratios, ticket-risk aggregates, tenure, cohort attributes).
Target column: `churn_within_horizon` (binary).

## Missing-data handling

- Accounts with zero tickets in a trailing window get `0.0` for all
  ticket-derived features (not `NaN`) -- absence of tickets is itself
  informative (a quiet account), not missing information.
- Accounts with insufficient login history for a given trailing window
  (e.g. a very new account) get `0.0`, not a dropped row -- dropping rows
  would bias the training set toward older accounts.
- `validate_table` fails any table with >5% missingness in a non-primary-key
  required column, rather than silently imputing at the validation layer.
