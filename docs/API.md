# API Reference

Base URL (local): `http://localhost:8000`. Interactive docs (Swagger UI)
are auto-generated by FastAPI at `/docs` once the server is running.

## `GET /health`

Returns service status and whether each artifact loaded successfully at
startup.

```json
{"status": "ok", "churn_model_loaded": true, "batch_decisions_loaded": true, "feature_store_loaded": true}
```

## `GET /accounts/{account_id}/churn-score`

Real-time churn scoring, looked up by account ID -- this is the realistic
version of "score this account right now": features are read from the
feature store the training pipeline already produced, not supplied by the
caller. A real caller (a CS console, an account page) has an ID, not a
20-field feature vector.

Response:
```json
{"account_id": 2216, "churn_probability": 0.0943, "model_version": "churn_advanced_model.joblib@1788143546"}
```

Errors: `404` if the account isn't in the latest feature-store snapshot,
`503` if the model or feature store hasn't been loaded (run the training
pipeline first).

## `POST /score/churn`

Real-time churn scoring for a caller that already has its own computed
feature vector (a different system, a what-if scenario, a feature not yet
materialized into the feature store) -- distinct from the ID-based lookup
above because it fails differently: this one 422s on a malformed feature
vector, the ID-based one 404s on an unknown account. See
`harbor.serving.schemas.AccountFeatures` for the full field list -- one
entry per column in `NUMERIC_FEATURE_COLUMNS + CATEGORICAL_FEATURE_COLUMNS`.

Request:
```json
{
  "account_id": 1, "plan_tier": "growth", "industry": "retail",
  "employee_size_band": "small", "region": "na",
  "tenure_months": 12, "base_mrr": 199, "current_mrr": 199,
  "avg_login_trailing_3m": 5, "avg_login_trailing_6m": 20, "avg_login_trailing_12m": 30,
  "avg_api_calls_trailing_3m": 50, "avg_api_calls_trailing_6m": 200, "avg_api_calls_trailing_12m": 300,
  "avg_feature_adoption_trailing_3m": 1, "avg_feature_adoption_trailing_6m": 3, "avg_feature_adoption_trailing_12m": 4,
  "login_trend_3v6": -0.5, "login_trend_6v12": -0.2,
  "ticket_count_trailing_3m": 3, "ticket_count_trailing_6m": 4,
  "avg_ticket_risk_proba_trailing_3m": 0.8, "avg_ticket_risk_proba_trailing_6m": 0.7,
  "avg_ticket_sentiment_trailing_3m": -0.4, "avg_ticket_sentiment_trailing_6m": -0.3,
  "low_plan_and_declining": 1
}
```

Response:
```json
{"account_id": 1, "churn_probability": 0.1025, "model_version": "churn_advanced_model.joblib@1787916165"}
```

Errors: `422` on missing/invalid fields (Pydantic validation, e.g. an
unrecognized `plan_tier`), `503` if no trained model artifact is loaded.

## `GET /accounts/{account_id}/decision`

Batch lookup: the pre-computed decision from the latest
`run_batch_scoring.py` run.

Response:
```json
{
  "account_id": 42, "churn_probability": 0.062, "predicted_uplift": 0.031,
  "expected_value": 14.1, "recommended_action": "no_action",
  "scored_at": "2026-08-28T11:23:19+00:00",
  "model_version": "churn_advanced_model.joblib@1787916165"
}
```

Errors: `404` if the account wasn't in the most recent batch-scoring run,
`503` if batch decisions haven't been computed yet.

## Versioning

`model_version` is `{artifact filename}@{file mtime as unix timestamp}` --
enough to tell whether a response came from before or after a retraining
run without standing up a full model registry. See `docs/LIMITATIONS.md`
for what a real model-registry integration would add.
